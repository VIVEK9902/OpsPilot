# OpsPilot - Interview Preparation

## A. Project Overview
**Q: What is OpsPilot and why did you build it?**
A: OpsPilot is an enterprise operations platform that combines support ticketing, order tracking, and an AI assistant. I built it to solve the disconnect between knowledge retrieval and actual execution — providing an AI that can not only answer questions via RAG but safely take actions using secure Tool Calling.

## B. Architecture
**Q: Why a Modular Monolith instead of Microservices?**
A: To maximize developer velocity and minimize operational overhead. By keeping modules (auth, tickets, ai) in the same codebase, I avoided distributed transaction complexities and network latency, while still maintaining strict domain boundaries using DTOs.

## D. Database
**Q: How are you handling AI memory and knowledge retrieval?**
A: I use PostgreSQL with the PGVector extension. This allows me to store high-dimensional embeddings generated by OpenAI alongside my relational data, reducing the need for a separate dedicated vector database.

## F. AI & Safety
**Q: How do you ensure the AI doesn't perform unauthorized actions?**
A: The AI never talks directly to the database. It can only emit a request to call a predefined tool (e.g., `cancelOrder`). That tool is backed by a deterministic Spring `@Service` method that enforces JWT validation, role-checking, and ownership rules before execution.

## I. Observability
**Q: How do you trace AI hallucinations or bad actions?**
A: Every state-changing action and every tool call is logged in the `AuditLog`. Furthermore, AI interactions are bound to correlation IDs, so I can trace exactly what prompt triggered which tool call.
